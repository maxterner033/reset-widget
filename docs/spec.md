# Мак-виджет: лимиты Claude Code + Codex

## Цель
Плитка на рабочем столе / в сайдборе виджетов macOS (не menu bar), которая всегда видна сама по себе — не нужно заходить в Claude/Codex или чекать вручную. Показывает 5-часовые (session) лимиты и время до их сброса для Claude Code и Codex.

## Требования к проекту
- Своя реализация, не готовое чужое приложение — пишется вайбкодингом (Claude), чужие репозитории используются только как референс структуры/архитектуры.
- Без затрат: без Apple Developer Program ($99/год), без App Groups.
- Минимальный практичный рефреш — упёрлись в системный лимит WidgetKit.

## Архитектура (решено)
Схема без App Groups — через прямую запись в контейнер виджета:

1. **Источник данных**
   - Codex: токен уже лежит в `~/.codex/auth.json` (залогинен через `codex login`). Данные о лимитах брать через локальный `codex app-server`, метод `account/rateLimits/read` — тот же источник, что у `/status` в CLI (не гадать эндпоинты).
   - Claude Code: аналогично — токен/сессия уже сохранены локально через `claude login`, читать оттуда.

2. **Host-приложение** (фоновый агент, без окна) — **реализовано 2026-09-09**
   - `LSUIElement = true` — без иконки в доке.
   - `@main struct WidgetResetApp: App` со сценой `Settings { EmptyView() }` (не открывается сама, нужна только чтобы удовлетворить протокол `App`) + `NSApplicationDelegateAdaptor` — никакого окна.
   - Автозапуск при логине — `SMAppService.mainApp.register()` в `applicationDidFinishLaunching`, проверено: приложение появляется в Системные настройки → Общие → Login Items & Extensions.
   - Не в sandbox → полный доступ к файлам.
   - Раз в 5 минут (`Task` с циклом `while` + `Task.sleep(for:)`) читает токены, тянет лимиты, считает %/время сброса, пишет снепшот. Код: `Host/Sources/Host/HostMain.swift`.
   - Пишет короткий JSON-снепшот (без refresh-токена) напрямую в контейнер **виджета** (`~/Library/Containers/<widget-bundle-id>/.../Application Support/`). macOS один раз спросит разрешение на запись в чужой контейнер — дальше без вопросов.

3. **Widget extension**
   - Ничего не запрашивает сам, никакой сети — только читает свой локальный JSON при каждом `getTimeline()`.
   - Timeline просит систему обновлять раз в 5 минут — это практический потолок для WidgetKit, дальше система сама троттлит (жёстче не выставить).

4. **Форс-рефреш по клику** — отклонено, решили не делать
   - Пробовали кнопку (⟳) внутри плитки через `AppIntent` (`Button(intent:)` + `WidgetCenter.shared.reloadTimelines`) — код компилировался и запускался, кнопка рисовалась, но клик не срабатывал. Причина подтверждена логом: `chronod: "There is no metadata for RefreshWidgetIntent in dev.maxterner.WidgetReset"`. Кастомные `AppIntent` в виджете требуют отдельный шаг сборки Xcode («Compile AppIntents Metadata», инструмент `appintentsmetadataprocessor`), который генерирует бандл `Metadata.appintents` — `xcrun --find appintentsmetadataprocessor` подтверждает, что в Command Line Tools его нет, только в полном `Xcode.app`. Без Apple ID/логина это не решить — нужен именно сам `Xcode.app` как источник инструмента.
   - Альтернатива без Xcode обсуждалась — `.widgetURL(_:)` (тап по всей плитке открывает Host по URL-scheme, без AppIntent-метаданных), но решили не делать: усложняет ради небольшой пользы, раз фоновый цикл и так обновляет данные каждые 5 минут.
   - Итог: форс-рефреша нет, полагаемся только на фоновый цикл Host (п.5).

5. **Реальная частота обновления данных** — реализовано, интервал 5 минут (см. п.2)
   - Host-приложение не ограничено WidgetKit-бюджетом — его свой таймер можно ставить чаще 5 минут, если нужно; он просто перезаписывает JSON, который виджет подхватит на ближайшем цикле или по клику.

## Обходы ограничений (важно учесть при реализации)

### 1. App Groups (обычно требует платный Developer Program)
Не используем вообще. Host-приложение (не в sandbox) пишет напрямую в контейнер виджета: `~/Library/Containers/<widget-bundle-id>/Data/Library/Application Support/`. macOS один раз спросит разрешение при первой попытке доступа к чужому контейнеру — после подтверждения работает без вопросов.

В снепшот копировать только необходимый минимум (по образцу CodexLimitsWidget): access token, account id, plan type, timestamp обновления. **Refresh-токен не копируется** — остаётся только в оригинальном `~/.codex/auth.json`, обновляет его сам host.

### 2. Подпись кода / Apple ID (обходим Xcode-провижининг)
Xcode IDE + автоматический signing требует Team (даже бесплатный Personal Team) и создаёт провижининг-профиль, который протухает через 7 дней.

Обход: собирать **не через Xcode-проект**, а напрямую через `swiftc` (Command Line Tools) и подписывать **ad-hoc**: `codesign -s -` (без Team ID, без Apple ID вообще). Работает, потому что архитектура не завязана на entitlements, требующие Team (App Groups, Push и т.п.).
- Плюс: не нужен Apple ID, нет 7-дневного протухания.
- Минус: при первом запуске Gatekeeper покажет предупреждение «неизвестный разработчик» — снимается один раз через правый клик → Открыть, либо `xattr -cr Widget.app`.
- Референс: так собирает `testpassword/CodexLimitsWidget` (`build-widget.sh`).

### 3. Частота обновления виджета (обходим троттлинг WidgetKit)
WidgetKit сам решает, когда реально вызвать `getTimeline()` — жёстко попросить чаще 5 минут нельзя, система троттлит. Обходим тем, что реальную работу (запрос лимитов, пересчёт) делает host-агент по своему таймеру (не ограничен WidgetKit), а виджет просто читает уже готовый JSON — данные могут обновляться чаще, чем перерисовывается сама плитка. Плюс форс-рефреш по клику (`AppIntent` → `WidgetCenter.shared.reloadTimelines`) для мгновенного обновления вне расписания.

## Производительность / нагрузка на систему
- Widget extension не работает как постоянный процесс — система запускает его коротко только для отрисовки, дальше он «спит». Основной нагрузки от него нет.
- Host-агент спит между циклами; раз в интервал: короткий subprocess `codex app-server` (спросил `rateLimits/read` → завершился, не держим процесс живым постоянно), лёгкий HTTP-запрос к Claude, запись небольшого JSON. Каждый цикл — доли секунды работы.
- Ожидаемый footprint: нативный Swift/AppKit-агент без UI — десятки МБ RAM, сопоставимо с обычными менюбар-утилитами (iStat Menus, Bartender), не с Electron-приложениями.

## Статус на 2026-09-09 (вечер) — блокер снят, виджет виден в галерее и показывает данные

**Обновление**: после двух фиксов ниже (SwiftUI Host + правильная точка входа `_NSExtensionMain`) виджет **появился в галерее** (Spotlight/Edit Widgets → «Widget Reset», обе плитки systemSmall/systemMedium показывают реальные данные: Claude 61%, Codex 60%). AMFI-ошибка `-423 adhoc signed or signed by an unknown certificate chain` и связанный с ней `chronod: purging ... isInternal? false` в логе — оказались не жёстким блоком, а сбоем первой попытки регистрации сразу после переустановки бандла; повторный вызов `getAllDescriptors` (без переустановки, без Xcode, без смены подписи) прошёл успешно. Вывод предыдущей версии этого раздела про обязательный сертификат "Apple Development" **не подтвердился** — ad-hoc подписи (`codesign -s -`) достаточно. Xcode/Apple ID для этого не нужны.

Что реально решило проблему (оба пункта обязательны):
1. `Host` был CLI-скриптом (`static func main() async` без run loop) — переписан в SwiftUI `App` с окном.
2. `WidgetExtension` собирался без флагов `-application-extension` / `-Xlinker -e -Xlinker _NSExtensionMain` — из-за этого точка входа была `_main` вместо стаба `_NSExtensionMain`, и процесс расширения падал почти сразу после запуска, не успевая ответить chronod. Флаги добавлены в `Package.swift` (`swiftSettings`/`linkerSettings` с `.unsafeFlags`).

Если виджет опять не появится после переустановки — судя по логу, стоит просто повторно открыть `.app` из `/Applications` (`open`) ещё раз или подождать несколько секунд: `chronod` иногда не кэширует дескриптор с первой попытки сразу после `lsregister -f`, но переспрашивает и успешно получает его при следующем обращении.

## Статус на 2026-09-09 (устаревший, оставлено для истории) — виджет не появляется в галерее

Сделано и подтверждено эмпирически (весь спайк Фазы 0):
- Claude Code: Keychain (`Claude Code-credentials`) → `GET /oauth/usage` — работает, `Always Allow` спрашивается один раз.
- Codex: `codex app-server` (без `daemon`/`proxy`, простой subprocess) → JSON-RPC по stdin/stdout (`initialize` → `account/rateLimits/read`) — работает, формат ответа см. `Host/Sources/Host/CodexAppServer.swift`.
- Host пишет объединённый снепшот прямо в `~/Library/Containers/<widget-bundle-id>/Data/Library/Application Support/snapshot.json` (без App Groups) — сработало, `Host` не в sandbox, разрешение спросилось один раз.
- `WidgetExtension` (SwiftPM-таргет, WidgetKit) собирается `swiftc`/SwiftPM без Xcode, бандл собирается вручную скриптом `scripts/build-widget.sh` (App.app + PlugIns/*.appex), подписывается — и **регистрируется в системе**: виден в `pluginkit -m -p com.apple.widgetkit-extension` наравне с системными и сторонними (Preply) виджетами, у него создаётся sandbox-контейнер.
- Дополнительно в этой сессии исправлены два реальных, но недостаточных для полного фикса дефекта (оба стоит сохранить):
  - `Host` был написан как обычный `@main struct HostMain { static func main() async {...} }` (CLI-скрипт, который завершался сразу после записи снепшота). Переписан в настоящее SwiftUI `App` (`Host/Sources/Host/HostMain.swift`) с окном и кнопкой "Обновить сейчас" + `WidgetCenter.shared.reloadAllTimelines()` — по образцу `testpassword/CodexLimitsWidget`.
  - `WidgetExtension` собирался SwiftPM-таргетом без флагов `-application-extension` и `-Xlinker -e -Xlinker _NSExtensionMain` — из-за этого точка входа бинарника была обычной `_main`, а не стаб `_NSExtensionMain`, и процесс расширения падал/завершался почти сразу после запуска (см. лог ниже), не успевая ответить `chronod` на `getAllDescriptors`. Исправлено в `Package.swift` через `swiftSettings`/`linkerSettings` с `.unsafeFlags`. Проверено через `otool -l` + `otool -Iv`: entry point теперь действительно указывает на lazy-stub `_NSExtensionMain`.

Но: **плитка всё ещё не появляется в галерее виджетов** (правый клик на столе → Edit Widgets) даже после обоих исправлений выше. Перепробовано и не помогло само по себе: иконка, `CFBundleDisplayName`, `NSExtensionPointVersion=3.0`, `lsregister -f`, установка в `/Applications` (а не в build-папке проекта), перезапуск `chronod`/`NotificationCenter`, self-signed сертификат вместо ad-hoc.

**Причина найдена и подтверждена системным логом** (не гипотеза — прямая цитата):
```
amfid: /Applications/Widget Reset.app/Contents/MacOS/WidgetReset not valid:
Error Domain=AppleMobileFileIntegrityError Code=-423
"The file is adhoc signed or signed by an unknown certificate chain"

chronod: (ChronoCore) Requested to add extension, but purging instead because
we shouldn't cache it: <WidgetExtension ... isInternal? false>
```
`amfid` явно отклоняет и ad-hoc, и локальный self-signed сертификат (оба варианта проверены и дают этот же код -423, т.к. ни один не цепляется к Apple CA). `chronod` явно отказывается кэшировать дескриптор виджета для таких "непроверенных" (`isInternal? false`) расширений — то есть плитка физически не может попасть в галерею без подписи, которая проходит проверку AMFI. Это и есть тот самый "План Б" из риска Фазы 0: нужен сертификат **"Apple Development"**, выпущенный через Xcode на любой Apple ID (даже бесплатный Personal Team, платный Developer Program за $99/год не нужен).

Проверено: `security find-identity -v -p codesigning` → `0 valid identities found` — в системе нет ни одного сертификата, которому доверяет AMFI, поэтому обойти это без Xcode нельзя (ни `openssl`, ни `security import` кастомного CA не дают цепочку до Apple).

**Следующий шаг**: поставить Xcode.app (App Store или developer.apple.com, ~ несколько ГБ), залогиниться любым Apple ID (Personal Team бесплатно), дать Xcode сгенерировать "Apple Development" сертификат (Xcode → Settings → Accounts → Manage Certificates → +), затем в `scripts/build-widget.sh` заменить `codesign --sign -` на `codesign --sign "Apple Development: <email> (<TEAMID>)"` для App и extension. Установка Xcode и вход по Apple ID — это действия, которые должен выполнить сам пользователь (логин с учётными данными Apple ID вне зоны автоматизации ассистента).

Технический контекст для следующей сессии:
- На машине нет Xcode.app, только Command Line Tools (`xcode-select` указывает на CLT). `WidgetKit.framework` в SDK CLT есть, компиляция работает.
- Codex CLI не в `$PATH`, лежит в `/Applications/ChatGPT.app/Contents/Resources/codex` — так его и резолвит `CodexAppServer.swift`.
- Собранный бандл: `build/Widget Reset.app` (в `.gitignore`), пересобирается `./scripts/build-widget.sh [debug|release]`. Для теста галереи бандл нужно ставить в `/Applications` (`ditto` + `lsregister -f`), в build-папке проекта `chronod`, судя по всему, тоже разрешает работу с расширением, но `/Applications` — это конфигурация, которая реально была протестирована.
- В login keychain уже лежит самоподписанный сертификат `WidgetReset Local Dev` (codesigning) — он не помогает (см. выше), можно удалить.

## Статус на 2026-09-10 (продолжение) — звук «лимит достигнут», надёжнее детект сброса, «вход истёк»

Нашли ещё один референс — `ArrivaRUS/claude-codex-limits` (менюбар-приложение, не WidgetKit-плитка, но зрелая реализация звуков/детекта). Проверили код (`Sources/LimitsMonitor.swift`, ~2800 строк, чистый AppKit) и забрали три вещи:

1. **[Host/Sources/Host/LimitReachedNotifier.swift](../Host/Sources/Host/LimitReachedNotifier.swift)** — новый независимый звук, когда любой лимит (5ч/нед, Claude/Codex) доходит до 100% (`usedPercent >= 99.5`). Состояние "уже был на 100%" персистентное в UserDefaults и не зависит от baseline первого запуска Host — если лимит был исчерпан, пока Host не работал, звук всё равно прозвучит на первом успешном чтении после старта. Неудачное чтение (`window == nil`) не трогает сохранённый флаг — иначе временный сетевой сбой ложно "забыл" бы, что лимит уже был достигнут.
2. **[Host/Sources/Host/ResetSoundNotifier.swift](../Host/Sources/Host/ResetSoundNotifier.swift)** ужесточён: раньше триггерил на любую смену `resetsAt`; теперь требует ОБА условия — время сброса сдвинулось вперёд больше чем на 60 сек **и** `usedPercent` реально упал (`newUsed <= oldUsed + 0.5`), плюс `oldUsed > 0` (нечего сбрасывать, если и так было 0%). Защита от дребезга API, где `resetsAt` может чуть пересчитаться без реального нового окна. Проверено отдельным логическим тестом (5 сценариев: первый запуск, рост в том же окне, дребезг `resetsAt` без сброса usage, настоящий сброс, `oldUsed=0`) — все прошли.
3. **`authExpired`** — новое поле в [Shared/Sources/Shared/Snapshot.swift](../Shared/Sources/Shared/Snapshot.swift) `ProviderUsage`. [ClaudeUsageAPI.swift](../Host/Sources/Host/ClaudeUsageAPI.swift) теперь различает HTTP 401/403 (`.unauthorized`) от прочих ошибок; виджет показывает "вход истёк" вместо общего "ошибка" ([WidgetResetView.swift](../Widget/Sources/WidgetExtension/WidgetResetView.swift)). Пока только для Claude (Codex через `codex app-server`, у него своя обвязка авторизации — не трогали). Токен не рефрешится сами — просто честно показываем, что нужен повторный `claude`/`/login`, вместо молчаливого "ошибка".

### Найдено эмпирически: два разных механизма "подстройки под стол" — не путать

1. **Системное тонирование (Automatic/Monochrome widget style)** — macOS красит уже готовый непрозрачный снимок виджета в один тон под обои, когда курсор не наведён. Это не наша прозрачность и не блюр — постобработка готовой картинки на уровне компоузера, применяется **ко всем** десктоп-виджетам разом (не настройка конкретного приложения, обойти для одной плитки нельзя). Из-за неё все 4 цветовые зоны баров схлопывались в один кремовый оттенок, а засечки 25/50/75 становились не видны. Проверено: при наведении курсора или переключении стиля виджетов на "Full Color" (System Settings → Desktop & Dock → Widgets) цвета возвращаются полностью корректно — баг был не в `barColor(forRemaining:)`, логика верна.
2. **`.containerBackground` + `Material` не даёт настоящего блюра рабочего стола.** WidgetExtension рендерит содержимое офф-процесс, в статичный снимок — у него нет доступа к реальным обоям позади себя. `.ultraThinMaterial` в этом контексте блюрит не стол, а пустой системный холст (белый в светлой теме) и в итоге читается просто как сплошная белая карточка. Первая версия глубоко "стеклянного" фона (`.ultraThinMaterial` + `blendMode(.overlay)`) из-за этого выглядела монолитно-белой даже в Full Color style. Живого просвечивания стола через API недоступно — это ограничение платформы (то же самое для виджетов Apple). Заменили на `.thickMaterial` (собственная матовая фактура материала, не "тает" в белый) без blend-режимов, плюс мягкий блик сверху-слева (`RadialGradient`) и лёгкое затемнение снизу-справа для объёма — имитация "матового стекла" без буквальной прозрачности. Итоговый компромисс, выбранный пользователем: сохранить Full Color (реальные цвета баров) + опаковую, но стилизованную под стекло карточку, вместо возврата к тонированному режиму.

`swift build --target WidgetExtension` чистый. Пересобрано `./scripts/build-widget.sh debug`, переустановлено в `/Applications` (Host убит и перезапущен), расширение перезапущено — готово к визуальной проверке пользователем на реальном рабочем столе. ## Статус на 2026-09-10 (продолжение) — поддержка стиля виджетов «Автоматически» (`.vibrant`)

Пользователь переключил System Settings → Desktop & Dock → Widgets на **«Автоматически»** (плитка тонируется под обои) и упёрся в две вещи: тёмный текст макета стал нечитаемым на тёмной подложке, а цветные бары «стали белыми».

**Уточнение к записи от 2026-09-10 выше.** Там сказано, что системное тонирование — «постобработка готовой картинки, обойти для одной плитки нельзя». Первая половина верна, вторая — нет. Обойти (отключить) действительно нельзя, но **подстроиться можно**: WidgetKit сообщает режим через `@Environment(\.widgetRenderingMode)`. В «Автоматически» это `.vibrant` — система обесцвечивает содержимое и подкладывает фон, вытянутый из обоев. Ошибка была не в том, что тонирование неуправляемо, а в том, что мы отдавали ему фиксированные цвета.

Что сделано в [WidgetResetView.swift](../Widget/Sources/WidgetExtension/WidgetResetView.swift) — medium теперь имеет две ветки оформления:
- `fg(_:)` отдаёт **иерархические стили** (`.primary`/`.secondary`/`.tertiary`/`.quaternary`) в `.vibrant` и точную палитру макета в `.fullColor`. Именно иерархические стили WidgetKit укладывает в свою vibrant-палитру и гарантирует контраст с выбранной подложкой — сам «белый по тёмному / тёмный по светлому» делает система, вручную день/ночь ловить не нужно. Эмпирически: системная тема на машине светлая, а vibrant всё равно отрисовал текст светлым под тёмную подложку — то есть режим ориентируется на подложку, а не на `colorScheme`.
- Фон: в `.vibrant` собственный градиент не рисуем (система его всё равно перекрывает) — отдаём `.fill.tertiary`. Белые капсулы вкладок и MORE там же заменяются на `.fill.quaternary`, тени гасятся.
- Засечки на барах в `.vibrant` скрыты: они светлые и сливались бы с такой же светлой заливкой.
- Красный у «ошибка»/«вход истёк» в `.vibrant` обесцветился бы до того же серого, что и подпись тарифа, — там тревожное состояние показывается контрастом (`fg(.primary)`), а не цветом.

**Цветные зоны в «Автоматически» невозможны — проверено экспериментом, а не только по документации.** В плитку временно вставлялась проба из пяти образцов, отрисованных в `.vibrant`: (1) обычный `Rectangle().fill(Color.red)`, (2) `Image` из битмапа с чистым красным (`CGContext` → `Image(decorative:)`), (3) SF Symbol с `.foregroundStyle(.red)`, (4) тот же красный битмап с `.widgetAccentedRenderingMode(.fullColor)`, (5) зелёный битмап с тем же флагом. **Все пять вышли одним и тем же обесцвеченным оттенком** — разница между 4 и 5 была только в яркости (зелёный светлее красного), не в цвете.

Отсюда важный вывод про `widgetAccentedRenderingMode(_:)` (есть в SDK, `macOS 15.0+`, значения `.accented/.desaturated/.accentedDesaturated/.fullColor`): **он относится только к режиму `.accented`** (тонирование иконок на домашнем экране iOS) и на `.vibrant` не влияет вообще. Не тратить на него время в следующий раз.

Значит, единственный оставшийся канал — яркость, и `barFill(forRemaining:)` кодирует ту же шкалу насыщенностью заливки: <25% ост. — 1.0, <50% — 0.85, <75% — 0.7, дальше 0.55. Чем меньше остаток, тем заметнее полоска. Настоящие красный/оранжевый/жёлтый/зелёный возвращаются только при стиле **Full Color**.

Проверено на живом столе скриншотами во вкладках «Claude» и «Оба»: до фикса текст сливался с подложкой (см. `crop_auto`), после — читается весь, включая PRO/PLUS и время обновления; разница яркости между зонами различима (43% заметно ярче 69%).

## Статус на 2026-09-10 (продолжение) — Keychain перестал спрашивать доступ после каждой пересборки

Жалоба: «каждый раз после сна ноутбука просит пароль к связке ключей, хотя я жму *Разрешать всегда*».

**Со сном это не связано.** `security show-keychain-info` показал у login-связки `no-timeout` — на сон она не запирается. Настоящая причина видна в ACL записи `Claude Code-credentials`:

```
access: 5 entries
    applications (24):
        0: /Applications/Widget Reset.app (OK)
             requirement: cdhash H"82de90cce8c2d7d4c771fe19132a923c623772a2"
        1: /Applications/Widget Reset.app (status -2147415734)
             requirement: cdhash H"c53ee920931af37a77d5bef2bff915ab213bad84"
        ... ещё 22 таких же, все мёртвые
```

У **ad-hoc-подписи** (`codesign -s -`) designated requirement — это голый `cdhash`, то есть хеш самого бинарника. Keychain привязывает «Разрешать всегда» именно к нему, поэтому любая пересборка = новое приложение с точки зрения системы, и разрешение спрашивается заново. Двадцать четыре записи — это двадцать четыре пересборки. Со сном совпадало потому, что после пробуждения фоновый цикл Host первым делом идёт за токеном, и диалог всплывал именно в этот момент.

**Решение — постоянный self-signed сертификат для подписи** (Apple Developer Program по-прежнему не нужен). Создан локальный сертификат `Widget Reset Signing` и импортирован в login-связку с доступом только для `/usr/bin/codesign`:

```
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 3650 -nodes \
  -subj "/CN=Widget Reset Signing/O=Local Dev" \
  -addext "basicConstraints=critical,CA:false" \
  -addext "keyUsage=critical,digitalSignature" \
  -addext "extendedKeyUsage=critical,codeSigning"
openssl pkcs12 -export -inkey key.pem -in cert.pem -out ident.p12 -passout pass:temp -name "Widget Reset Signing"
security import ident.p12 -k ~/Library/Keychains/login.keychain-db -P temp -T /usr/bin/codesign
```

[scripts/build-widget.sh](../scripts/build-widget.sh) теперь подписывает этим identity (`SIGN_ID`, переопределяется переменной окружения); если сертификата в системе нет — печатает предупреждение и откатывается на ad-hoc, чтобы сборка на чистой машине не падала. Приватный ключ (`key.pem`/`ident.p12`) намеренно **не** хранится в репозитории: он живёт только в связке ключей, а при утере сертификат пересоздаётся командами выше ценой одного нового запроса доступа.

Что изменилось в requirement:

```
было (ad-hoc):     designated => cdhash H"82de90cc..."
стало:             designated => identifier "dev.maxterner.WidgetReset"
                                 and certificate root = H"4009e9bc..."
```

`cdhash` исчез — требование больше не зависит от содержимого бинарника.

Важные детали, проверенные эмпирически:
- **Сертификату не нужен статус trusted.** `security find-identity -v -p codesigning` по-прежнему показывает `0 valid identities` (сертификат числится как `CSSMERR_TP_NOT_TRUSTED`), но `codesign` подписывает им без единой жалобы, и Keychain требование принимает. Возиться с `add-trusted-cert` и админским паролем не понадобилось.
- **Регистрация виджета не пострадала.** Это был главный риск, учитывая историю с AMFI выше. После переподписи `pluginkit -m -p com.apple.widgetkit-extension` по-прежнему показывает `dev.maxterner.WidgetReset.Widget`, оба процесса живы. Ещё одно подтверждение, что след с ошибкой `-423` был ложным.
- **Кнопка имеет значение.** В диалоге «Разрешать всегда» / «Отказать» / «Разрешить» запись в ACL добавляет только *«Разрешать всегда»* (левая). «Разрешить» пускает разово и не оставляет следа.

Проверка сделана делом, а не рассуждением:
1. После одобрения в ACL появилась 25-я запись — уже с `certificate root`, без `cdhash`.
2. Собран **release** (заведомо другой бинарник, `cdhash 874ad2f6...` против `82de90cc...` у debug) и проверен `codesign --verify -R=<требование из ACL>` — **удовлетворяет**. При ad-hoc это дало бы отказ.
3. Пересборка debug + переустановка + перезапуск Host: снепшот перезаписан свежими данными Claude через 4 секунды, диалога SecurityAgent на экране нет.

Мелочь, оставленная как есть: 24 мёртвые `cdhash`-записи в ACL никуда не делись. Они безвредны (система их просто не матчит), а чистка требует переписывания ACL с вводом пароля. Там же в связке лежит старый бесполезный сертификат `WidgetReset Local Dev` из ранней сессии — тоже не трогали.
